# The §0.3 invention checks — full adversarial records

Every mechanic invented beyond the blueprint’s letter was reviewed by a separate
agent instructed to argue that it violates the walls’ spirit — not to approve it.
This file is the transcript record the invention gate requires. Verdicts and the
fixes applied are summarised in DECISIONS.md; the evidence is here.

## Round 1 — the seven inventions of the first build pass

### maintenance-debt-drag — **FAIL**

**The strongest case against it, in the reviewer’s words:**

> This mechanic is the only thing in the engine that can take the season budget to zero, and I verified that when it does, the allocation screen contains exactly three actions. Of 79 authored non-floor action cost blocks in `content/sim/campaign/actions/`, ZERO cost no time and no energy — every one requires at least one pip of `timeStructure` or `energy`. `debtPenalty` subtracts an absolute 1/2/3 pips from a table whose range is 1–5, so at threshold 3 a depleted character loses 100% of both spendable currencies and at threshold 9 a *steady* character (all gauges at band 2 → 3 pips) also loses 100%. In that state the affordable menu is rest / wait / seek-help and nothing else — silent rails by the §11 definition — and `floorReport` returns `pass: true`, because the free floor set is itself three actions across three families (health, inner, threshold) and therefore satisfies "≥3 affordable spanning ≥2 families" by construction. The mechanized rails test is structurally incapable of detecting the state this invention creates. Worse, §5.2's depletion floor reads *gauges only* (`isDeeplyDepleted`), so the high-debt/mid-gauge zeroed-budget state does not trigger negative-arrival suppression; negative events keep arriving at the full cap of two per season, ordinary failure bands add `maintenanceDebt: 2` (weight 3, `batch-world-capacity-civic.ts:440`), and the compounding loop closes. Both adversarial fleets that set `maintenanceDebt: 9` (`tests/fleet.ts:143`, `tests/s13-pileup.ts:86`) also set every gauge to 0 in the same statement, so the depletion floor fires and the exact hole is never exercised. And the sentence published on /methodology to reassure the reader about all of this — "one missed season cannot reach the first threshold" — is false against the code: two negative arrivals each landing a `+2` band reach 4 from a clean start in one season. This is a despair screen arriving through the economy, disclosed inaccurately, and green-gated.

**BLOCKING (5)**

- *Engine honesty — /methodology publishes the whole machine (§6, §5.3)* — The published rule "one missed season cannot reach the first threshold" is false against the code; the first threshold is reachable in a single season from a clean start.
  - Evidence: `lib/sim/economy.ts:168` (ECONOMY_RULES, rendered verbatim by `components/reference/SandboxMethodology.tsx:85`) asserts it. But debt accrues through TWO channels, and the rule discloses only one. Beyond `bookkeeping()`'s +1 (`lib/sim/season.ts:721`), 130+ content records set `maintenanceDebt` directly in band effects, including `+2` on ordinary non-rare bands — e.g. `content/sim/campaign/events/batch-world-capacity-civic.ts:440`, a `failure` band of weight 3 on a capacity event. `MAX_NEGATIVE_ARRIVALS = 2` permits two such arrivals in one season. 2+2 = 4, before bookkeeping's +1. Threshold 1 reached, season 1, debt 0 → 5. §5.3's "one missed action never produces catastrophe" is asserted in a comment, never enforced anywhere in code.
- *Silent rails — §11 FORBIDDEN, §3.4 menu floor* — The drag can reduce time and energy to zero, at which point every authored non-floor action in the campaign is unaffordable and the floor set is the only playable thing — and the floor gate passes anyway, because the floor set alone satisfies the floor gate.
  - Evidence: I enumerated all 79 `contract.costs` blocks across `content/sim/campaign/actions/*.ts`: none costs zero time AND zero energy. `deriveBudget` (`economy.ts:77-93`) computes `max(0, PIP_TABLE[c][band] - penalty)` for time and energy. All gauges at band 2 with debt 9 → 3-3 = 0 time, 0 energy. All gauges at band 0 with debt 3 → 1-1 = 0. Both reachable. `floorReport` (`season.ts:207-223`) then computes `pass = missing.length === 0 && afford.length >= 3 && families.length >= 2` over an affordable menu consisting of exactly `act-rest-maintain` (health), `act-wait` (inner), `act-seek-help` (threshold) — three actions, three families, all `costs: {}`. Pass is guaranteed. S-10's per-season telemetry and S-13's worst-case sweep both consume this function, so no gate in the roster can observe the rails this invention builds.
- *§5.2 — the sandbox must not compose a despair screen out of legitimate parts* — The debt drag opens a second route to a zeroed budget that the §5.2 depletion floor does not cover, and the adversarial fleets are constructed so this route is never tested.
  - Evidence: `isDeeplyDepleted` (`lib/sim/effects.ts:181-186`) reads only `gauges`: `anyDepleted (v<=0) || twoThin (count v<=1 >= 2)`. `maintenanceDebt` is not a gauge. A character at all gauges = 2 with debt 9 has a zeroed time/energy budget and is NOT deeply depleted, so `selectArrivals` (`season.ts:246-300`) suppresses nothing and delivers up to two negative arrivals per season, whose failure bands add `maintenanceDebt` +1/+2 and step gauges down. Both drained sweeps that exercise debt 9 (`tests/fleet.ts:143`, `tests/s13-pileup.ts:86`) set every gauge to 0 in the same object literal, so `anyDepleted` fires and the suppression masks the hole. The one state this invention makes uniquely dangerous is the one state no fleet visits.
- *§5.2 stacking / §5.3 proportionality* — The drag is an absolute pip subtraction against a 1–5 table, so its severity is inversely proportional to the character's footing — it hits hardest exactly where the doctrine says the model must stop stacking.
  - Evidence: `PIP_TABLE` (`economy.ts:38-43`) grants 1..5 by band; `debtPenalty` returns 0..3 flat (`economy.ts:66-70`); `deriveBudget` subtracts it unscaled. Threshold 1 costs an abundant character 20% of time and energy, and a depleted character 100% of both. The three thresholds are described as a graduated ladder on /methodology and are not one: for a character at depleted or thin, the FIRST threshold is already total. Nothing in the code softens or floors this by band.
- *Engine honesty — disclosure a reader can check against the code (§6)* — Every in-play description of the mechanic understates it, the third threshold is described nowhere in play, and the drag is invisible on the instrument it modifies.
  - Evidence: `lib/sim/campaign.ts:337` at debt ≥3: "now costing you time every season" — but `deriveBudget` removes a pip of time AND a pip of energy at threshold 3 (`drag = c === 'money' ? 0 : penalty` applies to both non-money currencies at every threshold). `campaign.ts:338` at ≥6 says "energy as well as time", implying energy begins at 6; it began at 3. There is no line at ≥9. `lib/sim/parse.ts:173` repeats the time-only error in the campaign parse. `grep -rn "debt" components/sim/` returns nothing: the budget instrument — one of the six canonical instruments — renders fewer pips with no on-screen cause, and the vanished pips appear in no attribution entry, since the drag is neither a band-width modifier nor an effect source and so falls outside §3.10's computability rule entirely.

**CONDITION (2)**

- *§5.3 — neglect raises costs (does the mechanic model what it claims)* — `act-wait` carries `floor: true`, so allocating nothing clears maintenance debt at the same rate as actually maintaining. The counter tracks allocation intensity, not neglect.
  - Evidence: `season.ts:718-721`: `maintained = allocations.some(a => act?.family === 'health' || act?.floor)`. `content/sim/campaign/actions-floor.ts:115-131` defines `act-wait` (family `inner`, `floor: true`, `costs: {}`). A player who waits every season never accrues debt; a player who works hard every season accrues +1/season regardless of what they did about maintenance. This inverts the modelled claim, and it interacts badly with the rails finding: in the zeroed-budget state the mechanically optimal move is to wait, which is precisely the disengagement the drag was meant to punish. It is also the closest thing here to a play-intensity-responsive signal, though it stays character state and never leaves the run.
- *§6 — evidence labels on every sim rule and modifier* — The money exemption is disclosed but unlabelled, and is a designer's assertion presented as physics.
  - Evidence: `economy.ts:83-84` comments "debt is a load on the week, not a fine"; `ECONOMY_RULES` states it never costs money. Real deferred maintenance is overwhelmingly a money cost; exempting money protects the currency a player needs for rent, tuition and relocation. That is a mercy — disclosed, so not hidden, but presented as a fact about the world rather than a design choice. Every action carries an `evidenceLabel`; `ECONOMY_TABLE_ROWS`, `debtPenalty`, `DEBT_THRESHOLDS` and `REST_CONVERSION` carry none, though §6 requires one "on every sim rule and modifier".

**NOTE (1)**

- *Engine honesty — the published rest rule* — The published account of what rest does is inoperative in exactly the state the drag creates.
  - Evidence: `ECONOMY_RULES` (`economy.ts:169`): rest "convert[s] the capacity you did not spend into recovery — three unspent pips buy one band." At a zeroed budget `restRecoverySteps(unspent)` returns 0 (`economy.ts:148`). Recovery still happens, but only through `act-rest-maintain`'s band effects (`actions-floor.ts:70,78`) — an undisclosed second channel. The escape from the spiral exists (up to −3 debt/season: −2 band effect plus −1 bookkeeping) but it is not the one the reader was told about.

**Conditions the reviewer set:**

1. Make the published claim true or delete it. Either cap total per-season debt accrual (bookkeeping + all effects) at 2 so the first threshold genuinely cannot be reached in one season, or remove "one missed season cannot reach the first threshold" from ECONOMY_RULES and stop asserting §5.3's no-catastrophe rule in a comment that nothing enforces.
1. Floor the drag so it cannot zero the budget. Require deriveBudget to leave at least one pip of timeStructure and one of energy after the debt drag (standing upkeep may still take them — that is player-chosen and visible), or scale the penalty by band rather than subtracting absolute pips. As written, the first threshold costs a depleted character everything.
1. Make the floor gate able to see rails. floorReport must report affordable NON-FLOOR options separately, and S-10/S-13 must assert on that count. A pass that the three free floor actions satisfy on their own cannot distinguish an open sandbox from a locked one.
1. Extend the §5.2 depletion floor to the flow, not just the stocks. isDeeplyDepleted (or a sibling used by selectArrivals) must treat a debt-zeroed time/energy budget as deep depletion, so negative-arrival suppression engages in the high-debt/mid-gauge state.
1. Add the untested state to the fleets. tests/fleet.ts and tests/s13-pileup.ts must include a sweep with maintenanceDebt: 9 and all gauges at 2 (and at 1) — high debt WITHOUT gauge depletion — since the current sweeps mask the failure by triggering the depletion floor in the same statement.
1. Fix the in-play disclosure. campaign.ts:337 must say the first threshold costs time AND energy; add a line for the third threshold; correct parse.ts:173; and surface the drag on the budget instrument itself, naming maintenance debt as the reason the pips are gone, so the reader can check the instrument against /methodology.
1. Decide what maintained means and disclose it. Either drop `act?.floor` from the bookkeeping predicate so waiting no longer clears maintenance debt, or publish the actual rule ("any health-family or floor action clears a step") in ECONOMY_RULES, where the clearing condition is currently absent entirely.
1. Give the economy's modifiers evidence labels — the pip table, the debt thresholds and drag, and the rest conversion — and record the money exemption on /methodology as a stated design choice rather than a fact about the world.

**What survived the attack:** Three walls I attacked hard and could not break. (1) The reader-subject wall holds: `maintenanceDebt` is a single integer in per-run `SimState` (`schema.ts:711`, initialised 0 at `lib/sim/campaign.ts:136`), read only by `debtPenalty`, `bookkeeping`, two briefing lines, one parse line, and the internal S-10 satisfaction measure — which the blueprint explicitly sanctions as never rendered. It is never aggregated across runs, never persisted outside the run's own save, never used to tune bands, weights or event mix, and never rendered as characterisation of the person. The nearest proxy I could construct (finding 6: it tracks how hard the player allocates, not what they neglected) is a property of the character within one run, not of the reader. (2) Determinism and fork isolation hold: `bookkeeping` and `deriveBudget` are pure, consume no RNG, and depend only on state and the committed allocation list; forks carry their own `maintenanceDebt` in their own state. (3) No composite: debt is one named quantity in one domain, never combined with anything, never rolled up, never rendered as a number or a band on any surface — it does not create the derived cross-domain gauge §11 forbids. Beat containment, the never-command five, and the no-numeric-probabilities rule are untouched by this mechanic, and the floor set remains literally affordable at zero pips in every state I could reach.

### recovery-tie-derivation — **FAIL**

**The strongest case against it, in the reviewer’s words:**

> The blueprint asked for one thing and named the exact way it must not be satisfied: §3.4 step 5 (LITERAL, and on §11's LITERAL list) requires "at least one recovery- or endurance-flagged option TIED TO THAT FAILURE", and then says in the same breath "S-3 verifies the tie, not merely that rest exists." The unconditional tier-3 fallback does precisely the forbidden thing, and it does it inside the verifier. `recoveryRoutesFor()` appends `act-seek-help`'s two recovery-flagged options to every result before returning. I ran it: it returns two routes for the string `"totally-made-up-id"`. There is therefore NO record in the game — real or imaginary — for which it returns an empty array. S-3's tie assertion is `if (!routes.length) fail(...)` (tests/sim-gates-4.ts:382) and S-13's is `if (f.routes === 0)` / `if (!f.hasSupportRoute)` (tests/s13-pileup.ts:210-211). All three predicates are unreachable dead code. The invention did not merely permit an untied failure to ship; it disarmed both gates that were built to catch one, including S-13, the blueprint's own adversarial worst-case gate, whose whole job under §5.2 is to prove that every maximally-stacked state "still offers ... at least one tied recovery route." The gate now proves only that `act-seek-help` is present in the registry — which is the floor-set assertion, already made elsewhere, restated as if it were the tie. And this is not hypothetical: of 105 failure-capable records in shipped content, 65 surface no non-floor route at all, and 46 render a byte-identical block. The mechanic's shape also removes the author's ability to decline: `evt-mo-refuses` and `evt-lu-refuses` were deliberately given no ties — the correct authorial judgement that another person's "no" is not a setback with a remedy — and the invention overrides that silence to print "Ways on from here ... naming it to someone who might be able to do something about it" after a friend asked for space and the player pushed. That is the engine framing a refusal as recoverable by asking around, which is the §3.7 spirit if not its letter.

**What survived the attack:** Three things survive, and they survive cleanly. (1) Reader-personhood, question 1, is genuinely unbreakable here: recoveryRoutesFor(recordId: string) reads exactly one input — a content record id. It touches no gauge, no committed list, no season index, no seed, no session, no cross-run store; recoveryTieFor even discards the SimState it is handed. There is no direct read and no proxy, because there is no signal at all. It cannot be reader-performance-adaptive because it is not adaptive. (2) Determinism and fork isolation, question 4's second half: the function is pure over module-level frozen registries, consumes no RNG, mutates nothing, and produces the same array on every replay in every fork; it is invoked from the season result assembly (season.ts:560) after all commit handlers, so it cannot perturb draw ordering. (3) Beat containment holds: recoveryTies are built from out.filter(i => i.failure), and beats never enter `out` — they are a separate SeasonResult field fed by beatForSeason(), which returns a BeatRecord and not a SimEvent. No beat can acquire a recovery tie, and no tie can reach the beat channel. Nor does the invention introduce any composite, score, or ranking (question 5): it emits an unordered list of route references with no weight, no total, and no comparative language. And the floor set itself is not weakened — the invention leans on it rather than eroding it; act-seek-help remains floor:true, zero-cost, repeatable, and unconditionally available (actions-floor.ts:214-333, asserted at sim-gates-4.ts:418-428). The idea behind tier 3 is also defensible on its own terms: an always-present, always-affordable route to a real support page, shown after a setback, is a good thing to have on the screen. The failure is not that it is offered. The failure is that it is counted.

### rest-conversion — **PASS-WITH-CONDITIONS**

**The strongest case against it, in the reviewer’s words:**

> The hostile reading is available directly from the code and it is this: the game pays you for not spending your money, and pays it out as health. `restRecoverySteps` (economy.ts:148-149) calls `budgetTotal(unspent)`, which sums timeStructure + energy + money into one scalar (economy.ts:132). Three unspent *money* pips therefore buy a band of `healthEnergy` exactly as three unspent energy pips do. /methodology never says this — it says "three unspent pips buy one band of recovery" (economy.ts:169; SandboxMethodology.tsx:90-92), and a reader cannot derive currency-fungibility from that sentence. It also never says the conversion steps TWO gauges: season.ts:540 applies `{ healthEnergy: steps, timeStructure: Math.min(1, steps) }`, so at steps=1 two band-steps land while the rendered line says "a band of recovery" and the published rule says "one band." That is a mercy mechanic whose magnitude and inputs are misstated on the page that exists to make it checkable — hidden mercy wearing the disclosure's clothes, which §5.2 forbids by name.
> 
> Worse, the ceiling is the wrong bound and does not bound the thing it was invented to bound. `act-rest-maintain` costs zero pips (actions-floor.ts:33), has no failure band (only solid/mixed, both strictly positive plus maintenanceDebt reduction), and is unconditionally available. There is no cap on allocations per season anywhere in `CampaignApp` or `campaign.ts`. So adding rest to ANY allocation is a free Pareto improvement, and the conversion turns leftover flow — which §7.5 says explicitly "does not carry over" — into permanent stock. There is no gauge decay anywhere in lib/sim, so a band bought this way is permanent, and a band of healthEnergy/timeStructure is itself a pip per season for the rest of the campaign (PIP_TABLE). Six unspent pips at season 10 buy three band-steps, deterministically, with no draw and no variance, returning roughly forty pips over the remaining fourteen seasons. That is the single most efficient and least risky use of a pip in the game, and its price is not deciding. The ceiling caps steps per season; it does nothing to the strategy "take the free rest, spend down to exactly six unspent, repeat," which is what a ceiling of two bands actually creates. The invention's own comment calls the ceiling anti-exploit; the exploit it names is the one it leaves open.
> 
> And S-10d cannot see it. `POLICIES` (tests/fleet.ts:47-86) contains greedy-per-priority (width 3, never systematically resting), `rest-heavy` (slot 0 floor action, slots 1-2 filled with arbitrary spending — so unspent is small and the conversion rarely fires at value), `spend-everything`, `never-rest`, and `wait-only` (which leaves the whole budget unspent but takes `act-wait`, not rest, so it converts nothing). No policy in the fleet is "policy X plus the free rest action," and none is "rest plus underspend to the ceiling." The gate asserting "rest-heavy is never strictly dominated" is therefore satisfied trivially and reports nothing about the mechanic under review.
> 
> The sharpest doctrinal hit is the counter-incentive against the recovery tie. Because unspent is what pays, spending pips on a *priced* recovery action reduces the payout — and because of the ceiling, it only reduces it in the low-budget states. At budget 3/3/3 (nine pips), rest alone and rest-plus-a-three-pip-recovery-action both yield the capped two steps: spending is free. At budget 2/2/2 (six pips) — the drained states S-13 exists for — rest alone yields two steps and rest-plus-the-tied-recovery-action yields one. The engine pays the character more for declining the recovery route tied to their failure than for taking it, and it does so worst exactly where §3.4's recovery-tie rule and §5.2's worst-case promise are load-bearing. The tie is still offered and still affordable, so the letter holds; the spirit is that recovery is a live route in a bad season, and this quietly prices it.
> 
> Finally, the conversion narrates its own attribution instead of computing it. season.ts:547 hard-codes `[{ category: "choice", note: "you left room in the season on purpose" }]`. §6 says attribution is computed, never narrated, and S-12 asserts rendered factors equal the nonzero tagged components of a resolution — this item is not produced by the resolution atom at all, so it slips the assertion. The note is also false in reachable states. In a drained season where nothing on the menu was affordable, the game tells the player they left room on purpose. And the invalidation refund path (season.ts:479) adds a refunded cost back into `spent`, which inflates `unspent` — so an event outside the character's control (a layoff) can push the total over a threshold and hand out a band of health recovery attributed to "your choice," when §3.10's own classification rule says a systemic trigger renders as `systems`. That is the machine asserting an intention about the person at the keyboard, hard-coded to be true, in the state where it is least true.
> 
> None of this is unfixable and none of it is a crisis-tier or beat-channel breach, which is why this is not a fail. But as it stands the published rule does not match the code, the anti-exploit bound does not bind, and the mechanic prices the recovery route in the worst seasons. It must not ship in this form.

**What survived the attack:** The core wall holds: this mechanic does not read the person at the keyboard, directly or by proxy. Both inputs live in SimState and are per-run — `cs.sinceContact` is seasons since the CHARACTER last contacted that person (reset by an in-fiction allocation, lib/sim/season.ts:705), and node kind is a pure function of relationship-mark state that §3.7 explicitly sanctions as arc conditioning ("entry conditions keyed to relationship-mark state, player actions, and neglect/repair history"). Nothing here aggregates across runs, characterises tendencies, or tunes to how well the reader has been doing. The hostile reading — "the game watches how much attention you pay and pushes neglected people at you" — resolves to character state on inspection, and I could not make it resolve otherwise.

Determinism and fork isolation survive intact. selectArrivals is pure in `state`; the per-arc event draw is keyed by arc id (`selectionDraw(state.drawSeed, state.seasonIndex, \`companion:${arc.id}\`)`, lib/sim/season.ts:280) rather than by slot index, so the draw stream does not couple to sort order — a genuinely careful choice that makes the cap replay-stable. The sort comparator is total (`b.priority - a.priority || (a.arcId < b.arcId ? -1 : 1)`, never returns 0) so ordering is deterministic under equal priorities. No RNG outside the commit path.

Beat containment is untouched: beats are read by beatForSeason (lib/sim/season.ts:757) off a separate placement structure returning a BeatRecord, never a SimEvent, and cannot enter the arrivals list the cap operates on.

The floor set, the recovery tie, and the never-command five are all outside this mechanic's reach — the cap governs events, the floor governs actions, and no ordering rule touches option semantics.

And the empirical result is better than the design deserves: across 120 campaigns, leave nodes entered with a live event were delivered 133/133, refuse 119/120, deepen 89/90. No wall is currently unreachable. The problem is that this is luck of content shape (2-5 live arcs, single-eventRef nodes, leave bands all running to season 24), not something anything in the gate suite guarantees.
